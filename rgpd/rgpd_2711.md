- Sous-traitants : base SQL configurée via `SQLALCHEMY_DATABASE_URI`. Pas de transfert hors UE connu à ce stade.

## Description des traitements

### Gestion des comptes et authentification
- Finalité : création et administration des comptes utilisateurs.
- Base légale : exécution du contrat/CGU ; intérêt légitime pour la sécurité (vérifications et blocages).
- Données traitées : id, email, username (optionnel), display_name (optionnel), role (`client|admin|super_admin`), hash de mot de passe (bcrypt), horodatages de création.
- Modalités d'authentification prévues :
  - Enregistrement via `/users` ; mot de passe stocké en hash bcrypt (salage géré par la librairie).
  - Authentification par jetons JWT Bearer (définition dans `utils/swagger.py`) via l'en-tête `Authorization: Bearer <token>`.
  - Tokens courts + refresh (7 jours) ; aucun token conservé côté serveur, hors logs techniques.
- Destinataires : équipe technique habilitée uniquement ; pas de partage avec des tiers.
- Conservation : données du compte conservées tant que le compte est actif ; la suppression sur demande entraîne la suppression des partages et contenus reliés via les contraintes ON DELETE CASCADE.

### Gestion des contenus (notes, collections, flashcards, tags, liens, partages)
- Finalité : fournir le service de prise de notes, d'organisation et de partage.
- Base légale : exécution du contrat (service demandé) ; consentement explicite pour tout partage public ou ciblé.
- Données traitées :
  - Notes : titre, contenu libre, visibilité (`private|public`), propriétaire, horodatages.
  - Collections : nom, description, visibilité, propriétaire, horodatages.
  - Flashcards : question, réponse, lien vers la note.
  - Tags : nom du tag et liens notes/collections.
  - Partages : liens note/collection -> utilisateur, permission (`read|write`), horodatage.
- Destinataires : par défaut le propriétaire ; d'autres utilisateurs uniquement si le partage est créé ; public si visibilité = `public`.
- Conservation : tant que le compte propriétaire est actif ou jusqu'à suppression par l'utilisateur ; la suppression du compte entraîne la suppression du contenu et de ses partages.

### Journalisation technique
- Finalité : sécurité applicative et diagnostic.
- Base légale : intérêt légitime (art. 6-1-f RGPD).
- Données collectées : timestamp, méthode et chemin HTTP, User-Agent tronqué à 50 caractères, statut HTTP, durée, taille de réponse (voir `utils/logger.py`).
- Fichiers : `logs/app_info.log` et `logs/app_error.log`. Pas d'IP stockée nativement.
- Conservation : purge/anonymisation des logs au plus tard sous 6 mois.

## Mesures de sécurité en place
- Mots de passe stockés uniquement en hash bcrypt ; aucune conservation en clair.
- Contraintes de base de données (unicité email/username, cascades de suppression, validation des enums de rôle/visibilité/permission).
- Séparation info/erreur dans les logs ; pas de stockage des corps de requêtes.
- Exposition Swagger sécurisée par schéma Bearer ; CORS actif pour le frontend autorisé.

## Droits des personnes
- Droits : information, accès, rectification, effacement, limitation, portabilité, opposition.
- Effacement et portabilité : suppression de compte => suppression des notes/collections/tags/partages liés ; logs techniques anonymisés ou supprimés selon la politique de conservation.

## Conservation et archivage
- Comptes et contenus : conservation pendant la durée d'usage du service ; effacement sur demande ou après clôture du compte.
- Logs techniques : purge temporelle (<= 6 mois).

## Analyse des risques et mesures à prévoir
- Risques : accès non autorisé à la base, récupération de contenu partagé publiquement, attaques par brute force sur l'authentification.
- Mesures existantes : hashage fort des mots de passe, rôles/permissions (`read|write`, visibilité `private|public`), pas de données sensibles par défaut hors contenus libres saisis par l'utilisateur.
- Mesures à ajouter : limite de tentatives de login et journalisation des échecs, tests de sécurité et revue de code régulière.
